## 实现和验证

### 实现保持适度

围绕已确认的问题修改，复用项目已有机制。不为一次局部需求增加通用框架、未来兼容层或无调用方的配置。

在不可信输入、外部服务、持久化数据等边界做必要校验。内部已有明确类型或调用约束时，不逐层重复检查；只有独立入口或真实失效路径才补防护。不使用宽泛异常捕获、静默默认值或无限重试掩盖错误。确有恢复需求时，明确恢复条件和失败结果。

“不做过度防御”不等于删除权限验证、输入校验或数据完整性保护。每项新增防护应能说明它处理的真实来源和失败后果。

### 按连贯修改安排测试

先明确本次成功标准和最相关的现有检查。修 Bug 时，能低成本复现就先运行定向用例；需要时补充回归测试，确认它能区分修复前后。

完成一项连贯修改后再验证，不每改一行就运行全部检查。调试期间可以反复运行正在失败的定向测试。按以下范围选择起点，而非一次启动所有层级：

| 变更 | 默认验证范围 |
| --- | --- |
| 拼写、说明文字 | 检查差异与相关链接；涉及渲染时看渲染结果，不新增业务测试 |
| 安装或操作步骤 | 核对实现和前提；可行时执行受影响的最短路径 |
| 局部逻辑或 Bug | 相关单元测试或回归用例，覆盖触发条件及关键正常路径 |
| 接口、共享逻辑、配置或依赖 | 受影响调用方与模块测试，必要时构建或集成验证 |
| 权限、数据迁移、跨模块行为 | 针对威胁或数据不变量的测试，以及必要的集成验证 |

仅在测试失败暴露更广影响、公共契约改变、影响范围不明或仓库明确要求时扩大范围。轻量完整测试若比筛选更便宜，也可直接运行；不要绕过必需检查。

避免同时启动多套高负载或共享数据库、端口、目录的测试。默认先运行最有信息量的一组，资源允许且互相独立时再并行。

测试断言用户可观察行为或关键不变量，不复写实现、不为覆盖率堆叠同义用例。已有测试覆盖需求时优先复用。不要批量更新快照来消除失败而不检查差异。

相关检查和必需检查通过，且没有新修改或未解决疑点时停止。后续变更只重跑会受影响的检查；不为增加信心反复运行相同全套测试。环境导致失败时定位原因并说明影响，不无限重试或顺手扩大修复范围。
